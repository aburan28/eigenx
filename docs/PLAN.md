# EigenX build plan: end-to-end Eigen-Séta with a cryptanalysis programme

Status key: `[ ]` not started, `[~]` in progress, `[x]` done, `[-]` deferred.

## What "working end to end" means here

1. A user can generate a key pair, encrypt a file to it, and decrypt it, from
   the command line, at every parameter set, with keys and ciphertexts stored
   in a versioned binary format.
2. Every build is checked against known-answer vectors so the algorithm
   cannot drift silently.
3. Decapsulation never panics on hostile input and always returns the
   implicit-rejection key for anything that is not an honest ciphertext.
4. The security claims are written down with their evidence, every known
   attack family has a cost estimate at each parameter set, and the
   estimates that can be tested at toy scale have been tested.
5. There is a parameter set whose *quantum* cost against every known attack
   is at least 2^λ, not only its classical cost.

## Honest framing

No cryptanalysis programme run by the designers can "validate" a scheme.
What it can do is: enumerate the attack surface, cost every known attack with
stated assumptions, run the attacks that are runnable at toy scale to confirm
the cost model's shape, and state clearly what remains conjectural. External
cryptanalysis is the step after this one; `docs/SECURITY.md` is written to
make that step easy to start.

## Phase A: end-to-end usability

- [x] A1. `SecretKey::to_bytes` / `from_bytes` (zeroising), and
      `EigenSeta::secret_key_from_degree` so that the fact "the secret key is
      a function of the secret degree f and public data" is explicit in code
      and reusable by the cryptanalysis module.
- [x] A2. `eigenx` CLI (`src/bin/eigenx.rs`, no new dependencies):
      `keygen`, `encaps`, `decaps`, `encrypt`, `decrypt`, `info`, `params`.
      File format: magic `EIGX`, version, object kind, parameter-set id,
      payload.
- [x] A3. Deterministic DRBG (SHAKE256-based, `src/drbg.rs`) and
      known-answer tests `tests/kat.rs` with vectors in `tests/kat/`.
- [x] A4. Robustness tests: random ciphertext bytes, non-canonical field
      encodings, wrong-length inputs, cross-key decapsulation, implicit
      rejection is deterministic.

## Phase B: cryptanalysis

- [x] B1. `src/security.rs`: cost model. For each parameter set and each
      attack family, classical cost, quantum query count, and quantum gate
      cost under NIST MAXDEPTH ∈ {2^40, 2^64, 2^96} with the Grover oracle
      costed as one Kani chain. `examples/security_estimate.rs` prints the
      table; a test asserts each set meets its declared classical λ and
      records its quantum floor.
- [x] B2. `src/cryptanalysis/`: runnable attacks and checks.
      - key recovery by degree guess: derive the key from a guessed f and
        test it; confirms key = (f, public data) and gives the per-guess cost;
      - near-miss localisation experiment: for f' ≡ f (mod 2^k), k = 0..E,
        run a variable-time (2,2)-chain with splitting detection and record
        where (if anywhere) the chain splits early. The design note (§5.1)
        lists "no localisation" as unverified; this settles it at toy scale;
      - meet-in-the-middle on the sender's 3^F3-isogeny (generic message
        recovery): cost ∝ 3^{F3/2}; measured at toy sizes;
      - structural checks run on every generated key: f odd, gcd(f, 21) = 1,
        Δ' = 7f² odd (self-pairing attack excluded), eigenvalues distinct
        mod 2, pairing of the public basis is uniform in the odd residues
        (f is information-theoretically hidden by the eigenbasis scaling).
- [x] B3. Quantum-hardened parameter sets. The binding quantum attack is
      Grover over the FESTA-type mask space, cost d^{1/4}. Sets `Q3`, `Q5`
      take d = 3^F3 ≥ 2^{4λ} so that every known attack costs ≥ 2^λ quantum
      queries. There is no `Q1`: at λ = 128 the construction gives exactly
      the L5 prime, so L5 is the quantum-hardened level-1 set. Generated by
      `gen_params`; Q3 run end to end from the CLI (keygen 24 min, encaps
      9 s, decaps 9 min on one laptop core).
- [x] B4. `docs/SECURITY.md`: threat model, assumptions, attack table with
      costs per set, experiment results with the commands that produced
      them, and an explicit list of what is not established.
